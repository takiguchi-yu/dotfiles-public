## 振る舞いを決めるときは、仕様を先に書く

新機能・仕様変更・バグ修正で**振る舞い**を決めるときは、実装の前に仕様を書く。
書式（EARS・デシジョンテーブル・状態遷移表・契約）と網羅チェックは `spec-notation` スキルにある。
下の表に当たったら、依頼が無くても読む。「小さいから」は例外にならない。

### 何を書くか

当たった行はすべて書く。

| 条件 | 書くもの |
| --- | --- |
| 新機能・仕様変更で振る舞いを決める | EARS の要件（R1, R2…） |
| 振る舞いを決める条件が 3 つ以上組み合わさる | デシジョンテーブル（T1, T2…） |
| 状態が 3 つ以上あり、状態ごとに振る舞いが変わる | 状態遷移表（S1, S2…） |
| バグ修正・改修 | 直す振る舞い（EARS）と、変えない振る舞い（`[KEEP]`） |
| 公開インターフェース（関数・API・型）を新設・変更する | 事前条件・事後条件・不変条件 |
| スキル・CLAUDE.md などエージェント向けの文書 | 条件が 3 つ以上組み合わさるときだけデシジョンテーブル |

振る舞いが変わらない変更（リファクタ、typo、依存の更新、整形）は対象外。

### 書いたあと

- **置き場所は既存のものを使う** — チケットか `.scratch/<feature>/`（@ISSUE.md）、または to-spec / to-tickets の出力
- **ID ごとにテストを 1 件以上対応させる** — 完了条件（@ISSUE.md）は ID で書く
- **書いた仕様は報告に載せ、そのまま実装へ進む** — `[NEEDS CLARIFICATION: …]` が残ったときだけ、
  AskUserQuestion で聞いてから進む（@ASKING.md）
- **リポジトリに仕様の書式が既にあれば、そちらに合わせる** — 合わせたことは報告に 1 行残す（@PRACTICE.md）

### to-spec / to-tickets でも同じ書式で書く

第三者スキル to-spec / to-tickets のテンプレートに関わらず、この規定が優先する。

- **to-spec** — 振る舞いを書く箇所に、EARS の要件と、上の表で当たった表・契約を足す
- **to-tickets** — 受け入れ条件は、親の仕様の ID を参照して書く（例: `- [ ] #12 R3 を満たす`）
