## ユーザーへの質問は AskUserQuestion Tool で出す

ユーザーの返事を待つ事項（**未決**）は、必ず AskUserQuestion Tool で出す。
判定軸は疑問文かどうかではなく、**ユーザーの返事を待つ状態が残るか**。平叙文・命令文・箇条書きで書いても、返事を待つなら未決。

未決に当たるもの:

- **方針を選ばせる**: 案 A / 案 B、対象ファイル、実装アプローチ、どこまでやるか
- **前提の確認を求める**: 理解が合っているか、対象に含めるか
- **不足情報を求める**: 環境名、ID、対象範囲、期待する出力形式
- **続行の承諾を取る**: このまま進めるか、先に別の作業をするか
- **不可逆な操作の許可を求める**: 許可プロンプトが別に出る場合も、判断材料の提示はツールで行う
- **論点を保留したまま置く**: 依頼待ち・判断待ちの論点を本文に残すこと

自由記述で答えてほしいときも、想定される答えを選択肢にして、自由入力は「Other」に任せる。

本文に書くのは、**ユーザーの返事が無くても次へ進める**報告・提案・前提の明示:

- 「X と仮定して進めた。違えば直す」— 仮定を置いて作業を完了させた報告
- 「Y を確かめるため `cmd` を実行し、結果は Z だった」— 確かめた事実の報告（確かめられないときは @EVIDENCE.md の 4）

**迷ったらツールを使う側に倒す。** 「慣習的なデフォルトがあるなら聞かずに進めよ」というツール定義側の既定より、このルールを優先する。
ただし仮定を置いて作業を完了できるかは @DECIDE.md で判定し、完了できるなら完了させて仮定を明示する。

### ターンを終える前に、未決をゼロにする

1. 応答を出す直前に本文を読み返し、未決を数える。判定は、**返事を待たずに自分で次の一手を実行できるか**。実行できるなら報告、できないなら未決
2. 未決が 1 件以上なら、AskUserQuestion を呼んでから応答を終える。本文に書くのは論点の要約と、推奨の理由（下の節）まで。背景・選択肢・判断材料はツール側に置く
3. 論点には、気づいたターンで聞く。ユーザーが気づいて聞き返す手間は、この規定が防ぎたいもの

**完了条件: 本文に残った未決が、すべて同じターンの AskUserQuestion の質問に入っている。**

### 質問は初見で答えられるように書く

**質問 UI が出ている間、本文は画面から隠れる。** 答える瞬間のユーザーは、この会話を読んでいない**初見**の人と同じで、
見えるのは `question` / `options` / `preview` だけ。判断に要るものはすべてそこに入れる。

`question` には次の 3 点をこの順に書き、答えを求める 1 文で終える。**3 点と最後の問いは、空行で区切った別の段落にする**（計 4 ブロック）。

1. **背景** — いま何の作業中で、何が分かり、どこで分岐が生じたか
2. **決めてほしいこと** — 何を選ぶのかを 1 文で
3. **答えで変わること** — 答えによって次に何をするか、何が変わるか

段落の中も読みやすくする。

- 手順・並列の項目・条件は、**1 行 1 項目の箇条書き**（`1.` `-`）にする

例:

```
`orders` の検索が遅い件で、原因は `created_at` にインデックスが無いこと（実行計画で全件走査）だと分かった。

本番に `CREATE INDEX CONCURRENTLY` を流してよいかを決めてほしい。

流すと:
- 作成中の数分は、書き込みの負荷が上がる
- 検索は数 ms に縮む見込み（テスト環境に同じインデックスを張った実測で 2 秒→3 ms）

本番に適用しますか？
```

ほかのフィールドと語の扱い。

- **`options[].label`** — 選ぶと何をするのかが分かる語にする（「案 A」ではなく「本番に今すぐ適用する」）
- **`options[].description`** — 選んだら何が起きるか（実行する操作、変わるファイル、失うもの）
- **呼び名** — 本文や会話の途中で付けた呼び名（R3、前者、さっきの件）は、`question` の中で一言定義してから使う
- **見た目の比較** — 図や表示例は案ごとに `options[].preview` に入れ、`question` には見る場所を書く

**完了条件: 初見の人が、`question` と `options` だけを読んで、
何を決めるのか、各選択肢を選ぶと何が起きるのかを言える。かつ、`question` に 3 文を超える段落が 0 件。**

### 推奨には理由を添える

推奨の理由は、**本文と `description` の両方**に書く。`description` だけでは伝わらなかった。

- **本文** — 質問 UI を出す前に、推奨の理由を 2〜3 点の箇条書きで置く
- **`description`** — 冒頭に「推奨: 〜だから」の形で 1〜2 文
- **根拠の種類が分かるように書く** — 既存の慣習（`path:line`）、公式ドキュメント、実測結果など（@DECIDE.md の根拠の種類）
- **他の選択肢と比べて書く** — 「『全件書き換える』より変更が少ない」のように、比べる相手をラベルで名指しし、他を選ばなかった理由が読み取れる形にする

### スキルのフォーマット指定より AskUserQuestion を優先する

スキルが質問の出力フォーマットを指定していても（「本文にこの形式で出せ」と明示していても）、**提示手段は AskUserQuestion Tool**。
スキルの記法は、ツールのフィールドへ写して満たす。1 回に複数問まとめて出す設計のスキル（例: grilling）も、まとめ方はそのまま、出し先だけツールに替える。

| スキル側の要素 | 写す先 |
| --- | --- |
| 質問番号（Q1, Q2 …） | `header` の先頭（例: `Q1 方針`） |
| 質問タイトル | `header` / `question` の「決めてほしいこと」 |
| 前置き・背景 | `question` の「背景」 |
| 質問本文・選択肢 | `question` / `options` |
| 推奨回答（「➡️ …」など） | `options` の先頭に置き、ラベル末尾に `(推奨)` |
| 自由記述の余地 | `Other` に任せる |
| 補足・根拠・トレードオフ | `options[].description` |

### 1 回 4 問の上限を超えるとき

AskUserQuestion は 1 回につき最大 4 問。超える分は、4 問ずつ複数回に分けて呼ぶ。

1. まず問数を減らす — 独立した選択は `multiSelect` や選択肢の統合で束ねる
2. 残りを重要度・依存関係の上流順に並べ、上位 4 問を 1 回目の呼び出しで聞く
3. 回答を得たら、続けて次の 4 問を呼ぶ。**いま必要な質問は、作業を再開する前に聞き切る**

先の回答しだいで不要になる・前提が変わる質問は後回しにしてよい。
本文で「残り 2 件は続けて聞く」と予告してよいのは、いま聞かなくても手が止まらないものだけ。
