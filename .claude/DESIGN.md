## 何を作るときもオブジェクト指向で考える

コードでも文書でも、**扱う対象を「実体」として切り出し、責務で分ける**。
手続きを上から書き下す前に、次の 3 点を決める。**これを設計パスと呼ぶ。**

1. **登場する概念とその名前** — 何が主役か。名前が付かないものは、まだ切り出せていない
2. **それぞれが何に責任を持つか** — 1 つの実体が変更される理由は 1 つ
3. **依存の向き** — 誰が誰を知ってよいか。逆向きの参照を作らない

**分かりやすさは、この 3 点が決まっているかで決まる。** 決めずに書き始めたものは、
コードなら読めず、文書なら伝わらない。設計パスはそのための道具であって、
コードだけの作法ではない。

### 設計パスを通す条件

次のいずれかに手を付ける**前に**、必ず通す。「小さいから」「一度きりだから」は例外にならない。

**コードを書くとき**

- 新しいファイル・モジュール・クラス・サービスを作る
- 公開インターフェースを変える（関数シグネチャ、型定義、API、設定キー）
- 責務を分割・統合する（ファイルを割る、クラスを寄せる、レイヤを足す）
- 同じ形の分岐が 3 つ目に増える

**文書・手順書・スキル定義・設定を書くとき**

- 新しい文書を起こす、章立てを決める
- 既存文書に節を足す（**どの節の責務か言えないなら、置き場所が間違っている**）
- スキル定義・設定ファイル・データ構造を組み立てる

文書での設計パスは、コードと同じ 3 点をこう読む。

| | コード | 文書 |
|---|---|---|
| 概念 | モジュール・クラス・値 | 何について書くか。章・節の主題 |
| 責務 | 変更される理由が 1 つ | 1 節 1 目的。他の節の仕事を奪わない |
| 依存の向き | 具象より抽象へ、外側から内側へ | どの節がどの節を前提にするか（＝読む順序） |

### 頭の中で済ませず、書き出す

設計パスは**実装・執筆の前に 3〜5 行で書き出す**。**書けないなら、まだ設計が終わっていない。**
「検討した」で通過してよい、という意味ではない。

### 語彙と検討表は oo-design スキルを読む

原則（単一責任・カプセル化・継承より合成・依存は抽象へ・値オブジェクト・深いモジュール）と
GoF パターンの検討表は `oo-design` スキルにある。設計パスを通すときに読む。

**スキルの description の書き方に関わらず、この規定が優先する。**
`codebase-design` の description は "Use when the user wants to design…" と
ユーザーからの依頼を条件にしているが、上の条件に当たれば**依頼が無くても読む**。
ドメインの言葉を揃える必要があれば `domain-modeling` も同様に扱う。

### 見送るときも記録する

**素直に書く判断のほうが多い。** 問題が先、パターンは後。
見送る基準は `oo-design` の「採らない判断の基準」を読む。当たるならパターンを入れず、そのまま書く。

ただし**見送ったこと自体は報告に 1 行書く。**
「Strategy を検討したが呼び出し元が 1 つなので見送り」。**無言で通過してよいという意味ではない。**

### 報告に書くこと

- 通した設計パス（概念・責務・依存の向き）
- 採用したパターン名と、それが解いた問題
- 検討して**見送った**パターンと、その理由（過剰設計を避けた判断も成果物のうち）
